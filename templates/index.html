Security Alerts
Detection rules: 3 booking failures from the same pseudonymous source within 60 seconds (HIGH); 8 or more booking attempts within 10 seconds from one source (MEDIUM, bot-like burst). Neither is proof of an attack. Alerts deduplicate per source per minute.

Incident investigation
  1. Open the alert's trace.
  2. Inspect the failed span and correlated logs.
  3. Check the source pattern and whether failures are legitimate.
  4. Record findings; use human review before blocking anything.
Traffic and attack scenarios
Every button sends real HTTP requests to this local server. The booking site and this dashboard share the same backend, so every run appears live in the charts, logs, traces and alerts.


Customer browsing
Loads events and two seat maps, like a visitor comparing shows.


Booking rush
Eight buyers race for the same seat at once. Exactly one wins; the rest get SEAT_UNAVAILABLE. A rush can also trip the failure alert - that is expected.


Repeated booking failures
Three bookings for an event that does not exist, raising the HIGH repeated-failure alert.


Bot burst
Twelve rapid-fire booking attempts in one burst, raising the MEDIUM request-burst rule used to flag scalper-style automation.


Malformed input
Broken JSON payloads a fuzzer or script might send. The server rejects each with INVALID_INPUT before any booking logic runs.


Logical components
Booking site: customer-facing event and seat booking pages.
Ticketing service: request lifecycle and booking confirmation.
Inventory service: seat lookup and atomic reservation.
Security monitor: repeated-failure and request-burst detection.
Observability dashboard: this page, fed live by the same backend.
These are logical components within one Python process, not distributed microservices. No payment module, auth service or cloud exporter is connected.
